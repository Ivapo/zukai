### Round 2 — Phase 1 only — 2026-08-20 — same reviewer, resumed — **READY** (converged)

**Zero blocking. Converged within the cap: `status: accepted`, Phase 1
`reviewed = 2026-08-20`.** Phases 2–4 remain unreviewed and each needs its own
episode before it can be planned.

All five of round 1's blockers were verified fixed **from the file, not from the
changelog**. The reviewer re-derived the two claims the author had asked it to
scrutinise and both held:

- **The pure export-target function is genuinely node-testable.** Its inputs are
  a format, `state.currentPath` (string or `null`) and `state.doc.metadata.name`
  (`"Untitled"` for a fresh document, via `state.ts:initialState` →
  `emptyDocument`); its only dependency, `document.ts:withExtension`, is pure
  string manipulation. Nothing in filename/format/MIME reaches `document`,
  `Blob` or `URL`, so `vitest.config.ts` stays `environment: "node"` and no new
  dev dependency is implied. That is only true *because* the scope requires the
  decision to be extracted from the delivery — the requirement is load-bearing,
  not stylistic.
- **`export.test.ts` is the right witness for "the SVG builder was not
  touched".** Every one of its `diagramSvg` call sites passes a literal `Rect`
  or `null`, and it imports `./export`, `./geometry`, `./state` and
  `../model/types` — never `files.ts`. So it is insensitive to the seam
  refactor and sensitive to the builder, which is exactly what the gate asserts
  of it. Baseline re-measured green: 5 files, 493 tests, `node` environment.

Five new non-blocking findings, **all folded in**:

1. §2.1 said "every non-portable call in `model/` and `network/`… and there are
   three", then named two that live in `persist.rs`, outside both trees. Inside
   those trees the count is one. Rewritten to scope the claim to the crossing
   Rust and state both counts.
2. §2.2's "marked in two places and open in nine" — nine is the command total;
   seven are open. Corrected.
3. §2.6's "embedded into every exported SVG" — `export.tsx:diagramSvg` gates the
   `@font-face` block on `needsText`, so a textless diagram carries no font.
   Qualified.
4. The `menuInstalled` tri-state this spec had just introduced was the wrong
   answer to its own trap: the surface being varied is **host**-shaped, not
   menu-shaped, so synchronous `isTauri()` avoids the start-up flash outright
   and needs no tri-state. Scope now says so, and records that `menuInstalled`
   remains what `App` uses for the Cmd/Ctrl chords. *This is the round's own
   §7.3 trap in miniature — a round-1 fix introducing a worse mechanism than the
   problem needed.*
5. `installCloseGuard` returns `UnlistenFn | null` from `@tauri-apps/api/event`.
   The host interface must declare its own unsubscribe type or it puts a Tauri
   type name down the browser path — in the one phase that exists to keep it
   free of them. Added to scope.

**Rejections: none.** The one call recorded as *not changed* is the sizing

### Round 1 — Phase 1 only — 2026-08-20 — fresh reviewer, repo access — **NOT READY**

**Round 0 (asked once for this episode, per §7.0):** *Does this phase produce
the observable, and is it the right one?* **Yes.** Phase 1 puts a real road
figure — the observable this project exists to produce — in front of someone
with no app and no Rust toolchain, which is the reach argument §1 makes. And §1
confronts the `CLAUDE.md` doctrine test head-on (this spec makes no drawing
clearer and no drawing faster, and says so in its Goal) rather than assuming its
way past it, which is what §7.0 asks of a phase whose output is not itself a new
picture.

**Five blocking findings, all accepted, none rejected.** Two of them changed the
*shape* of the phase rather than its wording:

- **B1 — the premise for the in-page menu was simply false.** §2.2 asserted the
  file commands were reachable only from the native menu.
  `Toolbar.tsx:FILE_COMMANDS` renders New / Open… / Save / Save As… / Export…
  unconditionally in a `.file-actions` flex row, and `rules/persistence.md`
  already names that row as one of three trigger surfaces; only `onImport`
  ("menu-only, no toolbar button", its own comment) and Open Recent are
  menu-only. The phase had not said whether the new menu replaced the toolbar,
  sat beside it, or existed only for Import — three materially different apps.
  **Fix: no new menu component at all.** The browser needs the existing buttons
  working plus a reachable Import, which is a strictly smaller phase. A whole
  component was deleted from the plan before anyone built it.
- **B2 — the byte-identity gate was a tautology *and* unrunnable.**
  `files.ts:exportDiagram` builds `const svg = diagramSvg(...)` once, before any
  host-specific branch, so "the browser host's SVG is byte-identical to the
  Tauri path's" compared one expression with itself and could not detect drift;
  the only reading under which it asserted anything required each host to render
  its own SVG, contradicting §1.1's "no second renderer". Separately it could
  not execute: `measureDiagram` needs `getBBox`, a `Blob` host needs `document`,
  and `vitest.config.ts` is `environment: "node"` with no jsdom in
  `package.json`. **Fix:** the claim is deleted and replaced by a pure
  export-target function tested in `node`, `export.test.ts` passing unchanged as
  the builder witness, and an explicit *not claimed* clause naming
  `measureDiagram`'s `getBBox` / `document.fonts.ready` dependence as the reason
  byte-identity across WKWebView and Blink is false.

The other three forced a new **§2.7**, recording two decisions the phase had
left for an implementer to invent:

- **B3 — the host operation list was short by three, the command list by two.**
  `files.ts:confirmDiscard` calls `ask()`, `files.ts:report` calls `message()`,
  and `files.ts:installCloseGuard` calls `getCurrentWindow().onCloseRequested` —
  none path-shaped, so §2.2's "a dialog returns a path" framing hid all three.
  `newDocument` and `openRecentDocument` were missing from the enumerated
  commands. Fixed: the host is now
  `open, save, export, import, recents, confirm, notify, closeGuard`, and all
  nine exported commands are named.
- **B4 — "reports not available yet" could not happen.** `files.ts:report`
  swallows `message()`'s failure by design — "No Tauri runtime (plain
  `bun run dev`) — the console line above is it." Every browser error, including
  Phase 1's deliberate not-yet replies, would have been silent. Fixed in §2.7: a
  dismissible one-line in-page banner carrying `files.ts:detail`'s text.
  `alert()` ruled out — a modal blocks the page.
- **B5 — SVG vs PNG was undecided with no OQ covering it.**
  `export.tsx:exportFormat` reads the format off the extension of the path the
  save dialog returned; a browser download has neither. Fixed in §2.7: the
  browser gets two explicit commands, the desktop keeps its one dialog-driven
  command, and both still build the picture once so `exportDiagram`'s "the
  raster is this very file rendered by the webview" property survives.

Six non-blocking findings, all folded in: §2.1's blanket purity sentence (false
as written — `import.rs` has both `use std::fs` and `#[tauri::command]`);
`network_to_document`'s signature (it takes a `NetworkFile`, not a `&str` —
`parse_network` is the one taking the string); §2.3's overreaching "every
command takes a `path: String`" (`greet` and `recent_files` do not); §2.2's
"both already branch on `isTauri()`" (only two of nine commands do); a close-out
missing `rules/diagram-export.md`, whose declared `sources` already include
`files.ts`, `export.tsx` and `menu.ts` and whose `covers` names the pure/DOM/
Tauri layering this phase changes; and `rules/persistence.md` sitting at 121 of
its declared `max_lines: 122`, so a second host path needs a bump or a trim.

**Numbers:** the reviewer re-derived what the gate was keyed to and found no
literals — the behavioural check is "two nodes and a link", with no constant a
stated method must reproduce. Nothing passed for the wrong reason numerically.
