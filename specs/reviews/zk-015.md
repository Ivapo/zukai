## Rounds

### Round 3 — Phases 2 and 3 — 2026-08-21 — same panel, all three resumed — **READY** (converged)

**Zero blocking from all three reviewers. Converged within the cap: Phase 2 and
Phase 3 both `reviewed = 2026-08-21`.** Phases 4 and 5 remain unreviewed and each
needs its own episode.

Round 2's three newly-introduced blockers were verified fixed **from the files**:

- The count is satisfiable — 69 today (re-measured by two reviewers
  independently), 70 after the golden-writer. One reviewer sharpened *why* it is
  worth asserting: `persist.rs` carries **6** tests, so a `#[cfg]` gate applied
  one target too wide leaves a 63-test run that prints "ok" exactly like a
  69-test one.
- The golden asserts by default; the claim "the golden cannot rot without the
  Rust test going red" is now true of the test being specified.
- The Import split holds against the code: `state.ts:importDocument` takes
  exactly what `importNetworkFile` produces, `Canvas.tsx` already destructures
  `{ state, dispatch }`, and `Host.importNetworkText` keeps the codec out of
  `files.ts` without opening the cycle `host.ts` forbids. `import_network_text`
  also **self-enforces**: an unregistered `#[tauri::command]` is unreachable from
  the crate root and trips `dead_code` under the phase's own
  `clippy --all-targets -- -D warnings`.

Two things checked that had been taken on trust. The `mod persist` `dead_code`
concern was **not theoretical** — the round-1 wasm build emitted exactly
`VersionProbe is never constructed`, `migrate is never used`, `save_document is
never used`, `load_document is never used`. And Phase 3's observable argument
rests on a fact, not a rhetorical device: `Toolbar.tsx:BROWSER_COMMANDS` really
does render Open…, Save and Save As… in the browser row, and `host-browser.ts`
throws `notYet` for all three, so "three dead buttons" describes the shipped app.

### Round 2 — Phases 2 and 3 — 2026-08-21 — same panel, all three resumed — **NOT READY**

**The phase became two.** Round 1's largest finding was accepted and the phase
was split by **format**: Phase 2 is import-only, a new Phase 3 is `.zkai`, and
the deploy and landing pages renumbered to 4 and 5. Splitting by format rather
than by language keeps the observable in the first half — an imported network is
a picture, a saved file is not — and confines OQ-3 to the second. The
scope reviewer returned **READY**; the other two returned NOT READY on four
newly-introduced blockers, three of which the round-1 fixes had created.

**This round is the loop catching itself, twice, and both cases are §7.3's
warning in the flesh:**

- **The gate became arithmetically unsatisfiable.** Taking the stricter reading
  on `cargo test` made the number load-bearing — and the same phase adds a Rust
  test, so "still 69" went red on correct work. §7.3 says to re-measure a number
  in the same pass that newly keys a gate to it; this is what skipping that
  looks like. Found by two reviewers.
- **The cure for a tautological gate was itself tautological.** Round 1's fix
  specified a Rust test that *writes* the golden and asserts against it — which
  always matches itself. One reviewer noted this was the **third** appearance of
  that failure mode in this spec's record (round 1's B2 on Phase 1, round 1's N4
  here) and that it had landed inside the fix meant to cure it.
- **The drag-and-drop fix contradicted itself across two sentences**, and each
  escape broke something real: making `Host.importNetwork` return a `File` moves
  the desktop Import path (§1.1's first non-goal), while having `browserHost`
  call into `files.ts` opens the ESM cycle `host.ts`'s own doc comment forbids.
  Neither the picker's shape nor which side of the seam calls the codec was
  stated. Resolved by separating the two halves: the button keeps the shipped
  seam untouched, the drop gets `files.ts:importNetworkFile(state, dispatch,
  file)`, and a new `Host.importNetworkText` is where the codec is called —
  honoured by **both** hosts, so the seam carries no method a host refuses,
  which costs a five-line `import_network_text` command and is named as scope
  rather than discovered.

**One rejection, upheld by two reviewers on re-review.** A budget for OQ-4 was
declined: a threshold invented before the first measurement is a number with no
derivation behind it, and a gate keyed to it would be red or green for reasons
nobody could defend. One reviewer's framing is better than the author's and is
now in the spec — *the thing being bounded does not exist yet*.

### Round 1 — Phase 2 — 2026-08-21 — panel of three, fresh, repo access — **NOT READY**

**Round 0 (asked once for this episode, per §7.0):** *Does this phase produce the
observable, and is it the right one?* **Yes.** A real `network.yaml` becoming a
drawn junction with painted turn arrows in a browser tab is the road figure this
project exists to produce, and `CLAUDE.md` names "gets a real network onto the
canvas quickly" as import's entire justification.

A **panel** was run rather than one generalist (§7.1), because the phase changes
the Rust crate's build configuration, adds a wasm target and invents a test
harness. Lenses: correctness/grounding, exit-gate testability, scope/consistency.
All three returned NOT READY. Deduped: **8 blocking, 11 non-blocking.**

**The panel earned its cost on one finding.** Two reviewers inspected `build.rs`
and concluded it would probably not hard-fail; the third *applied the phase's
recipe in a scratch copy* and found it panics:

```
error: failed to run custom build command for `zukai v0.1.0`
  panicked at tauri-build-2.6.3/src/lib.rs:427:6:
  missing `cargo:dev` instruction, please update tauri to latest
```

`[build-dependencies]` are host-compiled, so a `[target.'cfg(…)']` table does not
touch them and `tauri_build::build()` still runs on wasm32. The phase named "so
the crate builds for `wasm32-unknown-unknown`" as its outcome while omitting the
one step that gets there — and the panic text misdirects toward a version bump.
A generalist round would have shipped this.

The other blockers, all accepted:

- **OQ-3 was unresolved and the phase branched on it**, by its own admission
  ("Blocks Phase 2's scope"). Not cosmetic: `Host.save` returns *where the
  document landed*, which `files.ts:adopt` feeds to `markSaved`. **Resolved by
  the author: download-only everywhere**, so `browserHost.save` returns `null`
  and Save is honestly Save-a-copy. The hybrid was declined because a
  `FileSystemFileHandle` is not the `string` that interface returns — it would
  reopen a seam Phase 1 shipped, for a capability two of four browsers lack.
- **The gate had nothing to compare against.** "Deep-equals the one the existing
  Rust import test produces" named a value that exists only inside `#[cfg(test)]`
  bodies; `CROSS_4` is a test const and no golden is committed anywhere. The
  `.zkai` half was worse — `save_document` only ever writes into a `tempdir()`,
  and the one committed `.zkai` is hand-authored, its README forbids
  regenerating it, and `migrate` runs on load, so a round trip through it is
  *guaranteed* not byte-identical. Fixed by having the phase **create** the
  artifact it compares against.
- **The gate was not sized to its blast radius** — it named three cargo commands
  and omitted `cargo test`, in a phase editing the modules 69 tests cover.
  `cargo check` never compiles `#[cfg(test)]` code at all. Rated blocking by one
  reviewer and non-blocking by two; the stricter reading was taken, and round 2
  proved it right by exposing the count contradiction.
- **Drag-and-drop had no seam** — nothing in `src/` accepts a dropped file, and
  Phase 1's seam is *pull*-shaped while a drop is *push*.
- **`canOpenDocuments` and `notYet` were never mentioned**, though
  `rules/host-seam.md` says the flag "goes away when Phase 2 lands the codec".
  Resolved with no rename and no split: the guard comes off `importNetwork`
  only, leaving the flag gating exactly the command its name describes.
- **The close-out omitted `rules/host-seam.md`**, the rule the phase most
  directly falsifies.
- **The phase was not one plan-mode pass** — 14 distinct workstreams across two
  languages against Phase 1's measured cost of 20 files and ~975 insertions in
  one language with no new dependencies. Split by format (see round 2).

Non-blocking, all folded in. The sharpest: **the gate's stated justification was
near-tautological** — "the two paths share a converter, and this is what proves
it" cannot fail on converter drift, because both paths call the same converter.
What it can catch is **marshalling** drift, which is the more valuable thing and
is now what the spec claims. That matters because `serde_wasm_bindgen` emits an
ES `Map` for a Rust map by default while `document.ts:normalizeDocument` indexes
plain objects, so `layout.nodes ?? {}` would pass a `Map` straight through and
every lookup yield `undefined` — a blank canvas that throws nothing.
`Serializer::json_compatible()` is now a recorded decision.

Also folded: OQ-4 re-tagged *(design call)* and explicitly **not** a gate item;
§2.2 given a dated `CORRECTED` note per §6.1 rather than a rewrite, since it is
the argument that produced Phase 1 and is no longer a description of the repo;
§2.1's shell count scoped to the Rust that *crosses*, with `lib.rs:run` and
`greet` named and excused rather than recounted; `migrate`/`VersionProbe` noted
as **private**, so Phase 3 is an extraction into pure `encode`/`decode` rather
than a visibility change; and the fixture path corrected to `src-tauri/tests/…`.

**Numbers re-derived and confirmed by more than one reviewer:** `cargo test` 69;
`cross-4.yaml` carries 16 movements; junction `node_id: N5`; the shipped import
test pins 8 turn-arrow markings on `L1/L1/L4/L4/L5/L5/L8/L8`;
`rules/host-seam.md` 122/150, `network-yaml.md` 313/315, `persistence.md`
130/132. Toolchain confirmed present locally (`wasm-pack`, the
`wasm32-unknown-unknown` target), so both gates are runnable here.

### Round 2 — Phase 1 only — 2026-08-20 — same reviewer, resumed — **READY** (converged)

**Zero blocking. Converged within the cap: `status: accepted`, Phase 1
`reviewed = 2026-08-20`.** Phases 2–4 remain unreviewed and each needs its own
episode before it can be planned.

All five of round 1's blockers were verified fixed **from the file, not from the
changelog**. The reviewer re-derived the two claims the author had asked it to
scrutinise and both held:

- **The pure export-target function is genuinely node-testable.** Its inputs are
  a format, `state.currentPath` (string or `null`) and `state.doc.metadata.name`
  (`"Untitled"` for a fresh document, via `state.ts:initialState` →
  `emptyDocument`); its only dependency, `document.ts:withExtension`, is pure
  string manipulation. Nothing in filename/format/MIME reaches `document`,
  `Blob` or `URL`, so `vitest.config.ts` stays `environment: "node"` and no new
  dev dependency is implied. That is only true *because* the scope requires the
  decision to be extracted from the delivery — the requirement is load-bearing,
  not stylistic.
- **`export.test.ts` is the right witness for "the SVG builder was not
  touched".** Every one of its `diagramSvg` call sites passes a literal `Rect`
  or `null`, and it imports `./export`, `./geometry`, `./state` and
  `../model/types` — never `files.ts`. So it is insensitive to the seam
  refactor and sensitive to the builder, which is exactly what the gate asserts
  of it. Baseline re-measured green: 5 files, 493 tests, `node` environment.

Five new non-blocking findings, **all folded in**:

1. §2.1 said "every non-portable call in `model/` and `network/`… and there are
   three", then named two that live in `persist.rs`, outside both trees. Inside
   those trees the count is one. Rewritten to scope the claim to the crossing
   Rust and state both counts.
2. §2.2's "marked in two places and open in nine" — nine is the command total;
   seven are open. Corrected.
3. §2.6's "embedded into every exported SVG" — `export.tsx:diagramSvg` gates the
   `@font-face` block on `needsText`, so a textless diagram carries no font.
   Qualified.
4. The `menuInstalled` tri-state this spec had just introduced was the wrong
   answer to its own trap: the surface being varied is **host**-shaped, not
   menu-shaped, so synchronous `isTauri()` avoids the start-up flash outright
   and needs no tri-state. Scope now says so, and records that `menuInstalled`
   remains what `App` uses for the Cmd/Ctrl chords. *This is the round's own
   §7.3 trap in miniature — a round-1 fix introducing a worse mechanism than the
   problem needed.*
5. `installCloseGuard` returns `UnlistenFn | null` from `@tauri-apps/api/event`.
   The host interface must declare its own unsubscribe type or it puts a Tauri
   type name down the browser path — in the one phase that exists to keep it
   free of them. Added to scope.

**Rejections: none.** The one call recorded as *not changed* is the sizing
judgement: the reviewer held its round-1 position that Phase 1 is one plan-mode
pass, on the grounds that the scope grew by three host operations but shrank by
a whole menu component. The author had explicitly invited it to re-raise sizing
as a blocker if it disagreed after the changes; it declined.

### Round 1 — Phase 1 only — 2026-08-20 — fresh reviewer, repo access — **NOT READY**

**Round 0 (asked once for this episode, per §7.0):** *Does this phase produce
the observable, and is it the right one?* **Yes.** Phase 1 puts a real road
figure — the observable this project exists to produce — in front of someone
with no app and no Rust toolchain, which is the reach argument §1 makes. And §1
confronts the `CLAUDE.md` doctrine test head-on (this spec makes no drawing
clearer and no drawing faster, and says so in its Goal) rather than assuming its
way past it, which is what §7.0 asks of a phase whose output is not itself a new
picture.

**Five blocking findings, all accepted, none rejected.** Two of them changed the
*shape* of the phase rather than its wording:

- **B1 — the premise for the in-page menu was simply false.** §2.2 asserted the
  file commands were reachable only from the native menu.
  `Toolbar.tsx:FILE_COMMANDS` renders New / Open… / Save / Save As… / Export…
  unconditionally in a `.file-actions` flex row, and `rules/persistence.md`
  already names that row as one of three trigger surfaces; only `onImport`
  ("menu-only, no toolbar button", its own comment) and Open Recent are
  menu-only. The phase had not said whether the new menu replaced the toolbar,
  sat beside it, or existed only for Import — three materially different apps.
  **Fix: no new menu component at all.** The browser needs the existing buttons
  working plus a reachable Import, which is a strictly smaller phase. A whole
  component was deleted from the plan before anyone built it.
- **B2 — the byte-identity gate was a tautology *and* unrunnable.**
  `files.ts:exportDiagram` builds `const svg = diagramSvg(...)` once, before any
  host-specific branch, so "the browser host's SVG is byte-identical to the
  Tauri path's" compared one expression with itself and could not detect drift;
  the only reading under which it asserted anything required each host to render
  its own SVG, contradicting §1.1's "no second renderer". Separately it could
  not execute: `measureDiagram` needs `getBBox`, a `Blob` host needs `document`,
  and `vitest.config.ts` is `environment: "node"` with no jsdom in
  `package.json`. **Fix:** the claim is deleted and replaced by a pure
  export-target function tested in `node`, `export.test.ts` passing unchanged as
  the builder witness, and an explicit *not claimed* clause naming
  `measureDiagram`'s `getBBox` / `document.fonts.ready` dependence as the reason
  byte-identity across WKWebView and Blink is false.

The other three forced a new **§2.7**, recording two decisions the phase had
left for an implementer to invent:

- **B3 — the host operation list was short by three, the command list by two.**
  `files.ts:confirmDiscard` calls `ask()`, `files.ts:report` calls `message()`,
  and `files.ts:installCloseGuard` calls `getCurrentWindow().onCloseRequested` —
  none path-shaped, so §2.2's "a dialog returns a path" framing hid all three.
  `newDocument` and `openRecentDocument` were missing from the enumerated
  commands. Fixed: the host is now
  `open, save, export, import, recents, confirm, notify, closeGuard`, and all
  nine exported commands are named.
- **B4 — "reports not available yet" could not happen.** `files.ts:report`
  swallows `message()`'s failure by design — "No Tauri runtime (plain
  `bun run dev`) — the console line above is it." Every browser error, including
  Phase 1's deliberate not-yet replies, would have been silent. Fixed in §2.7: a
  dismissible one-line in-page banner carrying `files.ts:detail`'s text.
  `alert()` ruled out — a modal blocks the page.
- **B5 — SVG vs PNG was undecided with no OQ covering it.**
  `export.tsx:exportFormat` reads the format off the extension of the path the
  save dialog returned; a browser download has neither. Fixed in §2.7: the
  browser gets two explicit commands, the desktop keeps its one dialog-driven
  command, and both still build the picture once so `exportDiagram`'s "the
  raster is this very file rendered by the webview" property survives.

Six non-blocking findings, all folded in: §2.1's blanket purity sentence (false
as written — `import.rs` has both `use std::fs` and `#[tauri::command]`);
`network_to_document`'s signature (it takes a `NetworkFile`, not a `&str` —
`parse_network` is the one taking the string); §2.3's overreaching "every
command takes a `path: String`" (`greet` and `recent_files` do not); §2.2's
"both already branch on `isTauri()`" (only two of nine commands do); a close-out
missing `rules/diagram-export.md`, whose declared `sources` already include
`files.ts`, `export.tsx` and `menu.ts` and whose `covers` names the pure/DOM/
Tauri layering this phase changes; and `rules/persistence.md` sitting at 121 of
its declared `max_lines: 122`, so a second host path needs a bump or a trim.

**Numbers:** the reviewer re-derived what the gate was keyed to and found no
literals — the behavioural check is "two nodes and a link", with no constant a
stated method must reproduce. Nothing passed for the wrong reason numerically.
